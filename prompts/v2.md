# jobq — v2 (single prompt, high give-away)

First run `cp ../../README.md ./README.md && cp ../../../WOLF-NOTES.md ./WOLF-NOTES.md`,
then read both files fully before writing any code.

You are a systems programmer writing **wolf**. Build the complete `jobq` tool as
`README.md` specifies, in the current directory (one module, one `main`). This prompt
hands you the **shape** of a good solution: the file layout, the job record and its
file format, the signatures, which filesystem operation makes each step atomic, and
the questions whose answers are the hard lines. The bodies are yours. Write the tests
and `test.sh`, and make every row pass.

## `store.lu`

```wolf
use std.fs
use std.str
use std.time

/// A job's record; the file is `key=value` lines, `cmd` as a JSON array of strings.
pub struct Job {
    id: int,
    cmd: List[str],
    added: int,
    tries: int,
    runner: str,
    lease: int,
    status: str,    // "", "ok", "failed", "killed", "lease-expired"
    started: int,
    ended: int,
    exit: int,      // -1 when absent
}

/// The rows a store call can raise.
error store_errors = {not_found, denied, exists, io, malformed}

/// The file name: a six-digit zero-padded sequence, then the id (the same number),
/// so that a sorted directory listing is id order.
pub fn file_name(id: int) -> str

/// Serializes a job; parses one (a missing or repeated key, or an unparsable number,
/// is `malformed`).
pub fn write_text(j: Job) -> str
pub fn parse_text(text: str) -> Job ! {malformed}

/// Allocates the next id (the highest sequence across the four state directories,
/// plus one) and creates the record in queue/.
pub fn add(dir: str, cmd: List[str]) -> int ! store_errors

/// Claims the pending job `name` for `runner`, then stamps the record in running/
/// with the runner and its lease.
pub fn claim(dir: str, name: str, runner: str, lease_ms: int) -> Job ! store_errors

/// Renews a running job's lease (the owner calls it every lease/3).
pub fn renew(dir: str, j: Job, lease_ms: int) -> () ! store_errors

/// Moves a running job to done/ or failed/ with its status and exit.
pub fn finish(dir: str, j: Job, status: str, exit: int) -> () ! store_errors

/// Running jobs whose lease is older than now: back to queue/ with tries + 1, or to
/// failed/ with status lease-expired once tries + 1 reaches max_tries. Returns the
/// names requeued. The attempt's log is renamed to log/<id>.<tries>.log.
pub fn reclaim_expired(dir: str, max_tries: int) -> List[str] ! store_errors
```

The two atomic steps, and the questions behind them:

- **Allocation.** Two `add`s can compute the same next id. Which `std.fs` call fails
  when the file already exists instead of truncating it, and what does the loser do
  with the `exists` row? Read `fs.lu` for the call and its rows (every row is answered
  by name; `?` through an alias is E0602).
- **Claim.** Two runners can see the same queued file. A rename is atomic: the one
  whose rename succeeds owns the job, the other sees `not_found`. Which comes first,
  the rename or the rewrite of the record with the lease, and why does the order
  matter? `fs.move_file` is the rename; read its doc on this pin, and if it copies
  rather than renames use the `fs_rename` builtin and say so.

`highest_id` lists the four directories with `fs.read_dir` and parses the six-digit
prefix; a file that does not parse is skipped, not fatal.

## `runner.lu`

```wolf
use std.process

/// One claim round: list queue/ sorted, try to claim up to `want` jobs, return them.
fn claim_round(dir: str, runner: str, lease_ms: int, want: int) -> List[Job]

/// Starts a job: process.command(cmd[0]), the args, stdout and stderr to
/// fs.create("{dir}/log/{id}.log") through set_stdout/set_stderr (read process.lu's
/// header for the fd table); returns the Child.
fn start_job(dir: str, j: Job) -> process.Child ! {unsupported, invalid, not_found, denied, io}

/// The loop: up to `jobs` children at once; between polls, renew leases for running
/// jobs every lease/3 and reclaim expired jobs of dead runners; exit when the queue is
/// empty and no child runs (unless follow). Returns 1 if any job failed, else 0.
pub fn run_jobs(dir: str, jobs: int, lease_ms: int, max_tries: int, follow: bool) -> int
```

Waiting on several children: `process.poll()` answers the next change if the pin has
it (read `process.lu`); else keep one `Child` per slot and `wait` on the oldest. The
runner's name is `"{host}:{pid}"` from `std.env.pid()` (host from `os_hostname` if it
exists at this pin, else `"local"`). When a runner dies with `kill -9`, what is the
sequence of events by which another runner picks the job up, and how long does it
take in the worst case?

## `argv.lu`

`split_line`: whitespace-separated words; single quotes take everything literally to
the next single quote; double quotes honor `\"` and `\\`; an unclosed quote is `quote`.
`json_argv`/`parse_argv`: a JSON array of strings with `\"`, `\\`, `\n`, `\uXXXX`
escapes (your own code; no `std.json`).

## `cli.lu`, `main.lu`

`ls` (sorted by id across the four states; `--state`), `show`, `retry` (`--failed` or an
id: move to queue/ with tries 0, status ""), `stats` (counts; mean and p95 of
ended − started over done/). Exit statuses as FR-12.

## Tests and acceptance

`jobq_test.lu`: `split_line` cases, the record round trip, two in-process claimers over
a temp dir (each of 50 jobs claimed exactly once). `test.sh`: A1–A2, R0, R1 (four
`jobq run -j 4 &` on one dir with 500 `sh -c 'printf x >> out/$1' _ <id>` jobs, three
repetitions: 500 files of size 1), R2/R3 (`kill -9` a runner after 1 s, `--lease 2`),
F1, M1, S1, P1, T1; `ok <row>` lines; non-zero on failure. Done means
`wolf fmt --check *.lu`, `wolf test .` and `./test.sh` exit 0; paste the last lines and
statuses.
